항목 2. 코드 구조 및 설계

Q. Quiz와 QuizGame 등 클래스들의 책임을 어떻게 나누었는가?

A. Quiz는 문제 하나의 데이터와 규칙을 담당한다. 문제, 선택지 4개, 정답, 힌트를 보관하고 생성 시 데이터를 검증한다. 또한 display()로 문제를 출력하고 check_answer()로 정답을 판정하며, to_dict()와 from_dict()로 JSON 데이터와 변환한다.

QuizManager는 퀴즈 목록, 최고 점수, 플레이 여부, 점수 기록을 관리한다. 퀴즈 추가·삭제와 state.json 읽기·쓰기도 담당한다.

QuizGame은 메뉴, 사용자 입력, 문제 수 선택, 랜덤 출제, 힌트 감점, 결과 출력 같은 전체 게임 흐름을 담당한다.

Q. 입력 처리, 게임 진행, 데이터 저장/불러오기 로직을 어떤 기준으로 분리했는가?

A. 사용자와 직접 상호작용하는 코드는 QuizGame에 두었다. 반복되는 숫자 입력 검증은 get_number()로 분리했고, 게임 진행은 play_quiz(), 추가는 add_quiz_ui(), 삭제는 delete_quiz_ui()로 나누었다. 사용자 화면과 무관한 데이터 저장·불러오기는 QuizManager로 분리했다.

Q. state.json 읽기/쓰기는 어디서 어떤 순서로 발생하는가?

A. 프로그램 시작 시 QuizGame이 QuizManager를 생성한다. QuizManager.__init__()은 load_state()를 호출해 퀴즈와 점수를 불러온다. 파일이 없거나 손상됐으면 기본 퀴즈 5개와 0점으로 복구한 후 save_state()를 호출한다.

퀴즈 추가·삭제 시에는 목록 변경 후 저장한다. 게임이 끝나면 record_game()이 점수 기록과 최고 점수를 갱신하고 save_state()를 호출한다. Ctrl+C나 EOF로 종료할 때도 현재 상태를 한 번 더 저장한다.

Q. Ctrl+C 또는 EOF 상황에서 안전 종료를 위해 어떤 처리를 했는가?

A. QuizGame.run()이 전체 입력 흐름을 try 블록으로 감쌌다. KeyboardInterrupt나 EOFError가 발생하면 run()이 예외를 처리해 안내 문구를 출력하고 save_state()를 호출한 후 traceback 없이 종료한다.

Q. 커밋을 어떤 단위로 나누었고, 커밋 메시지 규칙을 어떻게 정했는가?

A. 메뉴, 입력 검증, 상태 복구, 안전 종료, 힌트, 랜덤 출제, 퀴즈 삭제, 점수 기록, README 같은 하나의 기능·목적 단위로 커밋했다. 메시지 앞에 Feat, Fix, Refactor, Docs, Chore를 붙여 변경 성격을 표시하고, 뒷부분에 실제 작업 내용을 적었다.


항목 3. 핵심 기술 원리 적용

Q. 클래스를 사용한 이유는 무엇이며, 함수만으로 구현할 때와 어떤 차이가 있는가?

A. 퀴즈 하나의 데이터와 동작을 Quiz 객체로 묶으면 문제마다 서로 다른 상태를 가지면서도 같은 규칙을 사용할 수 있다. 또한 게임 흐름과 저장 책임을 QuizGame과 QuizManager로 나눠 코드 수정 범위를 줄였다.

함수만 사용하면 퀴즈 리스트와 점수를 매번 인자로 넘기거나 전역 변수로 관리하기 쉽다. 클래스는 상태와 메서드를 함께 묶어 책임과 소유 관계를 더 명확하게 표현한다.

Q. JSON 파일로 데이터를 저장하는 이유와 JSON 형식의 특징은 무엇인가?

A. JSON은 문자열, 숫자, 참·거짓, 리스트, 객체 구조를 표현할 수 있어 퀴즈 선택지와 점수 기록 같은 중첩 데이터에 잘 맞는다. 텍스트 형식이라 사람이 직접 읽기 쉽고, Python 표준 라이브러리의 json 모듈로 외부 패키지 없이 저장·로드할 수 있다.

Q. 파일 입출력에서 try/except가 필요한 이유는 무엇인가?

A. 파일이 없을 수 있고, 권한이 없거나 디스크 공간이 부족해 읽기·쓰기가 실패할 수 있다. 파일이 있어도 JSON 문법이 깨졌거나 필수 키와 값의 형식이 틀릴 수 있다. 이런 예외를 처리하지 않으면 프로그램이 traceback을 출력하며 종료된다. 현재 코드는 OSError, JSONDecodeError, KeyError, TypeError, ValueError를 처리해 기본 데이터로 복구한다.

Q. 브랜치를 분리해 작업한 이유와 병합(merge)의 의미는 무엇인가?

A. 브랜치는 기준 코드에서 독립된 작업 흐름을 만든다. 기능이 완성되기 전에 main을 불안정하게 만들지 않고, 변경 내용을 따로 검토할 수 있다. merge는 분리된 브랜치의 커밋 이력과 변경을 기준 브랜치에 합치는 작업이다. 이 저장소에서는 agent/git-merge-practice를 main에 --no-ff로 병합해 병합 이력을 그래프에 남겼다.

Q. state.json 데이터 구조를 현재 형태로 설계한 이유는 무엇인가?

A. 최상위에 퀴즈 목록인 quizzes, 최고 점수인 best_score, 플레이 여부인 has_played, 모든 게임 기록인 score_history를 두었다. 퀴즈 하나는 question, choices, answer, hint를 가진 객체이다. 이 구조는 퀴즈 정보와 게임 상태를 구분하면서 한 파일에 함께 저장할 수 있게 한다.

has_played를 별도로 두어 아직 플레이하지 않은 상태와 플레이했지만 0점인 상태를 구분했다. score_history의 각 기록은 played_at, quiz_count, score, max_score를 가지므로 문제 수가 달라지는 게임도 해당 게임의 만점과 함께 해석할 수 있다.


항목 4. 심층 인터뷰

Q. 퀴즈 데이터가 1000개 이상으로 늘어난다면 현재 JSON 저장 방식에 어떤 한계가 생길 수 있는가?

A. 현재 방식은 시작할 때 전체 JSON을 메모리에 올리고, 퀴즈 하나나 점수 기록 하나만 변경해도 전체 파일을 다시 쓴다. 데이터가 늘면 시작·저장 시간과 메모리 사용량이 늘고, 문제 검색·수정이 비효율적이며, 동시에 두 프로그램이 저장하면 변경이 유실될 수 있다.

규모가 더 커지면 SQLite 같은 데이터베이스로 퀴즈와 게임 기록을 테이블로 분리하는 것이 좋다. 필요한 행만 조회·수정할 수 있고 트랜잭션으로 저장 안전성도 높일 수 있다.

Q. state.json이 손상되어 JSON 파싱에 실패한다면 사용자가 데이터를 잃지 않도록 어떤 대응이 가능한가?

A. 현재 구현은 오류를 안내하고 기본 퀴즈로 복구해 프로그램을 계속 실행할 수 있게 한다. 다만 손상된 원본을 별도로 백업하지 않고 기본 데이터로 덮어쓰기 때문에 데이터 유실을 완전히 방지하는 구조는 아니다.

개선하려면 먼저 손상된 파일을 state.broken-YYYYMMDD-HHMMSS.json처럼 백업하고 기본 파일을 새로 만들어야 한다. 정상 저장할 때도 임시 파일에 먼저 쓴 뒤 완료되면 원본과 교체하는 원자적 저장을 사용하고, 최근 정상 백업을 여러 개 남기면 복구 가능성이 높아진다.

Q. 정답 채점 방식이나 퀴즈 구조 요구사항이 바뀐다면 어디를 먼저 수정해야 하는가?

A. 점수 규칙이 바뀌면 QuizGame.play_quiz()의 정답 20점, 힌트 10점 감점, total_possible, final_score 계산을 먼저 수정해야 한다. 그다음 QuizManager.record_game()에 저장하는 점수가 새 기준과 맞는지, state.json의 기존 점수를 변환해야 하는지 확인한다.

선택지 개수가 바뀌면 Quiz.__init__()의 선택지 4개 검증과 정답 범위를 먼저 수정해야 한다. 이후 QuizGame.add_quiz_ui()의 선택지 입력 횟수와 정답 입력 범위, play_quiz()의 입력 범위를 맞추고, 기존 state.json 데이터를 어떻게 변환할지도 결정해야 한다.
